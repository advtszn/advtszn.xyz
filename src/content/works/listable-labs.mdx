## The Product

Listable answers one question for brands: when someone asks ChatGPT, Gemini or Perplexity "what's the best X", do you show up? Every tracked prompt gets evaluated on a schedule across all three, the responses get classified into mentions, positions and share of voice, and the gaps between you and whoever outranked you get turned into concrete recommendations.

The classification problem sounds simple (given an LLM response, figure out which brands are mentioned and where) and it took four iterations to get right.

The first version was a two-pass LLM setup: one call generates the response, a second classifies it. Using an LLM to read another LLM's output felt like overkill, so we replaced it with something deterministic.

The deterministic version was a small markdown parser that walks the response, finds any ordered or unordered list, checks if the brand appears in it, and treats every other brand in the same list as a competitor and the sources and citation urls were extracted similarly. It was fast and free but non-semantic.

Brands don’t appear in responses under one canonical name; if wldd showed up as “wubba lubba dub dub” the parser counted it as no mention at all. Aliases, abbreviations and stylized names made the whole thing miss constantly.

And saving rankings for the competitors is worse, because a list item might be a bare company name or a full paragraph describing one, and the parser can’t tell the difference, so there’s no reliable way to know what the other items in the list even are.

So we went back to the two-pass LLM approach. That fixed accuracy but surfaced a different problem: raw API output isn't what users actually see in the consumer apps, which layer on search, tools and tuning the APIs don't have.

The final version evaluates responses as users see them (response that you'd get if you actually searched via the app, not the api), with a second pass that combines regex-based matching and LLM analysis to turn each answer into mentions, positions and cited sources.

## Background Jobs Without a Queue

All of this runs on background workers, and the obvious move was BullMQ or an equivalent. We skipped it because every queue library means another piece of infrastructure to run (Redis, in BullMQ's case) and MongoDB was already there.

Instead the prompts collection is the queue. Each worker is an infinite while loop that claims work with a single atomic `findOneAndUpdate`: find a prompt that's active, due for evaluation, and either unlocked or holding a lock older than the timeout, then set its lock timestamp in the same operation. Atomicity of the update is the mutual exclusion; two workers can race for the same prompt but Mongo guarantees only one wins.

A sort on priority and last-run time gives fair scheduling, a reaper marks runs that exceeded the lock timeout so crashed workers can't strand a prompt forever, and every run is audited into a jobs collection with a ULID run id, status log and the worker's pid and hostname. The same claim-with-a-lock pattern got reused for DNS verification and article generation workers.

## Multi-Tenant Blogs

<Screenshot src={multiTenantArchitecture} alt="Blog multi-tenancy sequence diagram: dashboard connects a domain, backend stores the CNAME record, a job polls for propagation, and the blog frontend resolves tenants from the Host header" />

Every project gets a hosted, GEO-optimized blog on its own domain. Honestly, this part was the most interesting one and simpler than it looked: connect a domain, add a CNAME record, and a background job verifies it.

Checking DNS records directly breaks the moment a domain sits behind a proxy like Cloudflare, since the CNAME is never visible. So instead of verifying the record, the job verifies the result: it requests the domain and checks for a challenge that only our frontend serves; if it comes back, the domain demonstrably routes to us. Domains get revalidated periodically, and TLS certificates are issued on demand via Caddy, so there's no provisioning step.

Once verified, one frontend serves every tenant. On each request the frontend reads its own Host header and calls the backend with that hostname; a backend middleware looks the domain up, resolves it to a project, and attaches that `projectId` onto the request context before any handler runs.

From there the handlers are tenant-agnostic, so the exact same code path serves a different blog depending only on which domain the request came in on.

What does that challenge actually guarantee? The obvious worry is a malicious actor standing up a site at the requested domain and serving us the nonce. To do that they’d have to make the challenge endpoint return the header, which means controlling either the domain’s DNS or the server it already resolves to. Anyone with that level of control can already do far worse than claim a blog, so domain control is the right gate.

## Closing the Loop with Google Search Console

Published articles are only useful if they get indexed, so the last piece connects each project to Google Search Console. The OAuth tokens are stored per project with automatic refresh, and the integration handles both GSC property styles (domain properties and URL-prefix properties) when matching the connected blog domain against the user's Search Console account. On publish, the blog's sitemap gets submitted against the matched property, so new articles enter Google's crawl queue without anyone opening Search Console.
